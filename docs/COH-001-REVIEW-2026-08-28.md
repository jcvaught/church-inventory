verified clean. Probes ran outside the repo.

## High

### H-1 — The legacy `tasks/` and `maintenanceTickets/` rule blocks are absent from the model

`maintenanceTickets` appears zero times in the 530-line document. Both legacy
blocks remain live in `firestore.rules` (lines 190–206 and 208–234) after the P2
cutover, and both still accept writes — measured: a member creates in `tasks/`
and an admin creates in `maintenanceTickets/` today.

The model proposes hardening `workItems`. If COH-002 implements that matrix on
`workItems` alone, a parallel unhardened path to the same conceptual data
survives with the full pre-COH-001 permission set. A stale client, a
copy-pasted path, or a deliberate actor writes there instead. Stage 3's smoke
checks as written would not detect it, because nothing exercises the legacy
paths.

Not rated Critical: the collections are empty today, so there is no live
disclosure — this is a completeness gap in the remediation surface, not an
active leak.

**Required:** bring both blocks into COH-002 scope, as deletion (preferred — P2
is documented complete and the collections were dropped) or identical hardening.
Add a tenth owner question if deletion needs approval.

### H-2 — The adversarial test plan asserts `list` denials the emulator cannot faithfully evaluate

The plan requires "Ordinary member cannot get or **list** raw people/access
records" and "Cross-tenant get, **list**, create, update, and delete remain
denied." This project has already been bitten here: the Firestore emulator does
not reproduce production `list` authorization faithfully and can fail open, so a
list-denial assertion can pass in the emulator while production differs.

Stage 2 is the gate before a production rules cutover, and the assertion most
exposed to this is precisely the People Access containment that the model ranks
priority 2. As written, that gate can return false assurance.

**Required:** state the limitation in the test plan and specify the technique —
get-only assertions plus the pointer-subcollection pattern already used
elsewhere in this repo — or mark list-denial as verifiable only against a real
project. Do not let an emulator pass stand as evidence for list containment.

### H-3 — AC-01 compounds AC-02, and the document does not connect them

Measured: an `active:false` profile with a live session can read
`accessRecords`. So the deactivated-account finding is not only "retains
inventory and reservation access" — an offboarded volunteer or dismissed staff
member retains read access to the church's background-check and certification
data.

The two findings are presented independently (AC-01 Critical, AC-02 High). Their
composition is the sharpest real-world scenario in the document and belongs in
the executive summary, because it changes the urgency argument: the exposure
that most warrants prompt owner attention is offboarded-person-reads-compliance,
not either finding alone.

Also measured for AC-01: `active:false` users can write the immutable activity
log and approve a pending reservation.

## Medium

### M-1 — AC-08's proposed fix may be infeasible, and no fallback is offered

AC-08 requires comment rules to "perform a parent document lookup and apply the
same visibility predicate." `firestore.rules:246–252` explicitly documents the
single-`get()` budget as the reason this was not done.

Firestore allows 10 document-access calls for a single-document request and 20
for a query. `userData()` already consumes one per evaluation. Rules are
evaluated per returned document on a list, so a parent `get()` per comment
exhausts the budget on any comment thread beyond a handful — the failure mode is
a denied query, not a slow one.

The model flags "rule read budgets and query behavior must be validated in
emulator tests," which frames a design risk as a validation step.

**Recommend:** carry an explicit fallback — denormalize `parentVisibility` and
`parentCreatedBy` onto each comment document at create time (rule-pinned or
server-set), making the check zero-`get` and list-safe. This also removes the
need to re-derive the predicate in two places.

### M-2 — The `active` remediation's lockout failure mode is under-specified

`userData().get('active', false) == true` denies any profile missing the field.
Measured: such a profile works normally today, so the change is a silent total
lockout for anyone in that state, not a degradation.

Stage 0 step 2 does query for this, which is the right control. Two refinements:

1. State the failure mode explicitly in the rollout section. "Verify all
   legitimate profiles have `active:true`" understates it.
2. There is partial existing evidence the field is near-universal: the `users`
   self-update rule reads `resource.data.active` bare, which errors when the
   field is absent, so any profile that has ever been self-edited must carry it.
   That narrows the at-risk population to profiles never self-edited (likely
   invite-created accounts that never touched Settings). Stage 0's query now has
   a predicted answer to check against rather than an open question.

### M-3 — The executive summary overstates the Storage/Firestore agreement

Summary item 1 says "Storage already requires `active:true`, so the two layers do
not agree." Storage requires it for **writes only** — `storage.rules` `allow
read` checks `churchId` alone, with no `active` predicate.

So a deactivated user retains read access in *both* layers, including item
photos. AC-01's body is accurate ("Storage writes are denied"); the summary
implies Storage is a working revocation boundary. The correction enlarges AC-01
rather than shrinking it, so it should not be left as a wording detail.

## Low

### L-1 — `users/{uid}` sits outside declared scope but inside AC-01's blast radius

Any member — including `active:false` — can read every same-church `users` doc,
`phone` included. AC-01's impact line mentions "user-directory" visibility, but
the collection is analyzed in neither matrix and is not in the scope statement.
Recommend an explicit scope exclusion or a matrix row, so COH-002 does not
inherit an unstated assumption.

### L-2 — Confirm "cancel own reservation" is a status change, not a delete

The current matrix correctly shows members have no delete on reservations, and
the proposed matrix grants "Edit/cancel reservation: Own Pending only." If the
UI's cancel is implemented as a delete anywhere, that row is not implementable as
stated. Worth confirming before COH-002 scoping.

## Assessment against the handoff's review criteria

- **Every current-rule claim validated against the pinned commit:** done for all
  claims I could test or read. No inaccuracies found; three imprecisions (H-3,
  M-3, and the `createdByName` nuance, which was correct).
- **Severity challenged:** AC-01 Critical is correct and under-stated (H-3).
  AC-02 through AC-07 ratings are appropriate. AC-09 Medium is right — forgery
  is real but the blast radius is attribution, not data.
- **Workflows represented:** yes. Volunteer, ministry-manager, room-approver,
  maintenance-assignee, and My Compliance all appear in the UI-dependency table
  with correct current behavior.
- **Rule-only/callable/data-model split technically sound:** yes, with M-1 the
  one place the split is likely wrong.
- **Missing abuse cases:** H-1 is the substantive omission. L-1 is a scope
  question.
- **Nine questions sufficient to scope COH-002:** nearly — with the additions in
  Questions 1 and 3 above.

## Verdict

**Approved with follow-up.** The model is accurate where I could check it, the
priority ordering is right, and the staged rollout is appropriately conservative.
The two High findings are additive rather than corrective: they do not invalidate
the analysis or the proposed matrix, and none of this requires rework.

H-1 and H-2 should land before COH-002 is scoped — H-1 because it would leave a
parallel unhardened path, H-2 because it would let a false emulator pass stand as
the gate for a production rules cutover. Neither blocks the product owner from
approving the target permission model now.
