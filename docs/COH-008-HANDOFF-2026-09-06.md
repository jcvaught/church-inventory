## Outcome

When a maintenance ticket, job, or task is deleted, the other side of the link is
now cleared by the server instead of by the browser. Three of the four cleanup
paths were failing silently in production before this: COH-006's rules deny the
reach-across when the actor cannot read the linked task, `jobListings` update is
admin/manager-only, and every client call was fire-and-forget — so each denial
was swallowed and surfaced later as a chip pointing at a deleted document.

This is the prerequisite that lets COH-007's archive freeze be total, with no
backlink allowlist (DEC-2026-017, plan amendment A18).

- Data/rules/API: **no Firestore rules change, no index change, no client

## Decisions and Assumptions

- Applied: **DEC-2026-017** (server-side fix, reciprocal checks mandatory) and
  plan amendment **A18** (the exhaustive five-row direction map).
- Decided during implementation, recorded in the workboard before review:
  `retry: true` means a permanently failing invocation would otherwise retry for
  24 hours, so only transient gRPC codes rethrow.
- Assumption made explicit: the trigger **fails closed on document shapes the
  current rules already permit**. Binding document id to `type` in
  `firestore.rules` would be a separate task and is deliberately not bundled.

**Not verified, and not to be reported as verified:**

  pessimistic transaction lock, so a write issued from inside the read/commit

  reason. Codex reviewed and **accepted** that reasoning, noting the property it
  would prove belongs to `runTransaction` rather than to this module.
- Nothing has been run against production.

## Risk and Rollback

- Main risk is a privileged write path. Three independent defences, all
  required: **reciprocity** (clear only when the target points back at the
  deleted document's bare id), **type routing** (follow only the fields
  belonging to the source's type), and **id/type binding** (a `type:'task'`
  source is accepted only at a `task_` id, and a work-item target's kind is read
  from its own data, never assumed from the path we built).
- Review trail: `docs/COH-008-IMPLEMENTATION-REVIEW-2026-09-06.md` (two High,
  one Medium, changes requested) → fixes →
  `docs/COH-008-IMPLEMENTATION-REREVIEW-2026-09-06.md` (**approved with
  follow-up**; H1, H2, M1 closed; the removed-race reasoning accepted).
- Rollback: delete the two functions. Nothing else changes — no rules, no
  indexes, no client code — and the client cleanups still run, so rollback
  returns exactly the pre-COH-008 behaviour.
- Production actions still requiring approval: **the Cloud Functions deploy
  itself.** Per `feedback_firebase_project` discipline, verify the Firebase CLI's
  active project and pass `--project church-inventory-9615c` explicitly; the CLI
  has been observed pointing at `courtclimber`.

## Known Limitations

- The four client cleanups (`src/useFirestore.js:758`, `:852`, `:1276`, `:1342`)
  **remain in place on purpose** (A18). They are harmless alongside the triggers
  because a reciprocal clear is idempotent, and they stay until both triggers are
  verified in production. Removing them is a later gate.
- The reservation-to-task direction has no cleanup on either side. Recorded in
  DEC-2026-017 as a pre-existing asymmetry, explicitly out of scope here.
- `firestore.rules` still permits a task document at an `mnt_*` id. The trigger
  fails closed on it; the rules were not tightened.
- Firestore triggers are not part of `SCHEDULED_JOB_REGISTRY` — that monitor
  covers scheduled jobs only. Failures surface via Sentry (`area:backlink-cleanup`).
