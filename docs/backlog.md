### OPEN QUESTION — can one human be more than one tracked `accessPeople`? (unresolved)
The `accessPerson.userId` link is **not** DB-enforced as 1:1, and we **do not yet know** whether a single human is ever *legitimately* tracked as two separate `accessPeople` docs (e.g. a paid **contractor** with an `hourlyRate` who is *also* a tracked **volunteer** with separate compliance). Until that product question is answered:
- **We are NOT enforcing 1:1.** Enforcing uniqueness would block the multi-tracking case if it turns out to be legitimate. The defensive aggregation below is the chosen model instead (and the server's `isAccessEligible` already aggregates).
- **Gating surfaces aggregate correctly across ALL of a uid's tracked docs** (2026-06-23): eligibility / `shiftReadiness` (Event-Day), `Person.complianceStatus` (Team Members badges), Settings → My Compliance. These read every `linkedTrackedIds` doc, matching the server.
- **Known remaining lossiness (display-only, currently latent — no multi-tracked data exists):** `buildPerson` still derives `roles`, `hourlyRate`, `personType`, `active`, and `contact` from the **first/representative** tracked doc only (see the comment in `src/lib/people.js`). `roles` would be the one unambiguously-correct thing to union across all docs; `hourlyRate`/`personType` are genuinely ambiguous under multi-tracking (a contractor rate shouldn't apply to a volunteer shift) and need a product rule, not a naive merge. **Do not "fix" these speculatively** — revisit only once the open question is answered and real multi-tracked data exists to design against. See `docs/AUDIT-POST-0611-2026-06-23.md` (MED-2) + CHANGELOG 2026-06-23.
