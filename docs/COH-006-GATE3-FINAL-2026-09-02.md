## Production probe review

### The query and listener evidence discharges the plan

The script constructs the exact five Gate-3 query shapes for each separately
authenticated account. Its asymmetric expected sets match the verification
plan exactly. It requires exact sorted IDs for all ten listeners and all ten
`getDocsFromServer` calls, rejects listener errors/timeouts, ignores cache-only
listener callbacks, requires server metadata, exercises all eight direct-read
controls and both cross-tenant denials, and merges the five server result maps
through `createWorkStore` to check completeness, union, and deduplication.

Listener-first ordering costs no intended evidence. The new app has no local
writes for the fixtures, the accepted listener callback must have
`fromCache === false`, and the listener is unsubscribed only after that exact
server set is observed. The subsequent one-shot read is separately forced to
the server and checked again. Ordering changes which independent mechanism runs
first, not what either one must prove.

Given the reported all-pass output, the run establishes compatibility of all
five query shapes with the deployed transitional rules, exact positive and
negative containment for these fixtures, server-backed listener behavior,
source overlap deduplication, stale-recipient exclusion, and a usable production
composite index. It does not establish the final Gate-4 authorization boundary,
as the verification plan already states.

### Low — the reusable harness encodes two weaker assertions than the plan

These do not invalidate this run because the implementation owner recorded the
stronger observed outputs: the exact Query Explain result had collection scope,
`visibility ASC`, `sharedWithUids ARRAY_CONTAINS`, and `__name__ ASC`, and final
cleanup reported zero work items.

For reuse, harden the script:

1. The Query Explain assertion at lines 230-233 merely string-searches for both
   field names. It must also assert collection scope and the `ASC` /
   `ARRAY_CONTAINS` modes (and should report, without hard-requiring, the normal
   `__name__` suffix).
2. Cleanup prints the remaining collection count but never feeds it to
   `check()`. Assert that the final count is exactly zero so incomplete cleanup
   cannot still exit with `PROBE PASSED`.

## Gate-4 assertions requested before implementation

Write these as direct SDK/emulator cases, split by actor rather than compressed
into one broad positive test. Production list containment must still be probed
after deployment because the emulator's list behavior is not authoritative.

### Final read rule

- Allow maintenance to an active same-church member.
- Allow a team task to an active same-church member.
- Allow a private/shared task to its creator and to a UID in a list-typed
  `assigneeUids`.
- Allow a shared task to a UID in a list-typed `sharedWithUids`.
- Deny an unlisted same-church member; deny inactive and cross-tenant users.
- Deny a stale `sharedWithUids` recipient when visibility is private.
- Deny malformed map/string projections; `in` over map keys must never grant.
- Preserve the deliberate absence of an admin override: an admin who is not
  creator, assignee, recipient, or covered by `team` cannot read a private or
  shared task.
- Remove the legacy missing-visibility read arm only after the current
  production delta verification remains zero.

### Update rule under DEC-2026-012

- Deny a same-church outsider's direct update that adds their own UID to either
  projection on a private task and on an unshared shared task. Assert the write
  itself is `permission-denied`, not merely a later read denial.
- Separately allow the creator, an existing shared recipient, an existing
  assignee, and a team member to add a third person's UID, with authorization
  evaluated from `resource.data` (the pre-update document).
- Add the admin-without-access negative case; role alone must not satisfy the
  pre-state visibility predicate.
- Require resulting `assigneeUids` and `sharedWithUids` to remain lists so an
  authorized direct caller cannot make the canonical authorization fields
  undeliverable or malformed.
- Retain and test `type`, `createdBy`, `taskNumber`, and `createdAt` immutability,
  and retain the existing separate restriction on who may change visibility.

### Comment gating

- For an unauthorized private-task member and an unlisted shared-task member,
  deny comment `get`, list/query, create, update, and delete.
- For the creator, assignee, and selected shared recipient, allow read/create;
  preserve author-or-admin update/delete only while that actor can also read the
  parent.
- Preserve maintenance comment read/create and the existing author/admin
  update/delete workflow.
- Test access revocation: after the actor loses their last parent authorization,
  deny subsequent comment reads and writes, including edits to their own old
  comment.
- Record comment author/name/timestamp spoofing as an explicitly accepted
  residual if Gate 4 does not pin it; parent gating must not be described as
  fixing attribution integrity.

After Gate 4 deploys, rerun the two-account negative controls against the final
rules, including an unconstrained old-client query expected to be denied. Also
publish the DEC-2026-012 Help Centre wording at that gate, without claiming that
the generic activity-log row names the person added unless logging is enhanced.
