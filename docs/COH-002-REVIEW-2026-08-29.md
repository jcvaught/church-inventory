## High

### H-1 — The `performedByName` pin silently drops audit rows, and breaks an existing e2e test

The rule requires:

```
request.resource.data.performedByName == userData().get('name', '')
```

Every page computes the value it sends as:

```js
const userName = userProfile?.name || "Unknown";
```

(`ItemsPage.jsx:159`, `SuppliesPage.jsx:74`, `ReservationsPage.jsx:166`,
`WorkBoard.jsx:604`)

When a profile has no `name` — or an empty one — the client sends `"Unknown"`
while the rule demands `""`. The write is denied. Measured, all three cases:

| Probe | Result |
|---|---|
| No-`name` profile sends `"Unknown"` | **denied** |
| Same profile sends `""` | succeeds |
| Correct profile sends a stale name | **denied** |

**This is not theoretical.** `scripts/setup-e2e-tenant.mjs:148–157` creates the
three E2E accounts with `email`, `role`, `churchId`, `active`, `allowedHubs`,
`createdAt`, `lastLogin` — and **no `name` field**. So every activity-log write
from an E2E account is now denied, and
`e2e/authenticated/crud.spec.js:14` — *"Admin can edit a job's location;
activityLog records update_job"* — asserts such a row appears within 15s. That
test fails against this SHA. Step 18 of the execution plan runs that suite.

**The failure is silent by design.** `logActivity` catches with
`handleErr(err, { op: 'logActivity', silent: true })`, deliberately, so the user
isn't shown a toast over an action that otherwise succeeded. The mutation
commits; only the audit row vanishes. That is precisely the failure mode
workstream 3 exists to prevent, reintroduced in a new form.

A second trigger: `userProfile` is a one-shot `getDoc` at auth-state change
(`useAuth.js:110`), not a live listener. If a name is changed out of band, that
session's cached copy is stale and every subsequent audit write fails silently
until the user signs in again.

**Required fix.** Change the four pages to send exactly what the rule expects:

```js
const userName = userProfile?.name ?? '';
```

Independently, `scripts/setup-e2e-tenant.mjs` should write a `name` — those
accounts are malformed relative to every account the app itself creates, and
that is worth fixing regardless of this rule.

**Worth considering, not required:** dropping the `performedByName` pin
entirely. The rule pattern is consistent with the existing `jobSwapRequests`
precedent (`firestore.rules`, `name == userData().get('name','')`), so following
it was reasonable. But the two paths differ in a way that matters: a swap
request is a rare, deliberate, user-initiated action with visible error
handling, while activity logging fires on every mutation and swallows its errors
by design. Pinning a mutable display string on a high-frequency silent path is a
worse trade than on a low-frequency loud one — and `performedBy` being pinned to
`request.auth.uid` already establishes authenticity. The name is denormalized
display text any reader can re-derive. Owner's call.

## Medium

### M-1 — `accessRecords` reads add a per-document `get()`; the budget is untested in production

```
get(/…/accessPeople/$(resource.data.personId)).data.userId == request.auth.uid
```

This resolves the parent per evaluated document. Firestore allows 10 document
accesses for a single-document request and 20 for a query, and `userData()`
already consumes one.

Probed at 5, 15, and 30 records for one person — **all pass**. The realistic
shape is benign: every record for a person resolves the *same* parent path, so
there is one distinct access regardless of count.

The caveat is the one this project already knows: the emulator does not
faithfully reproduce production query authorization, which is why COH-001's H-2
exists. **These budget results are not production evidence.** The risk is low,
but two cheap mitigations are worth taking:

1. Add a `limit()` to the self-scoped `accessRecords` query so an unexpectedly
   large record set cannot approach the ceiling.
2. Note the per-document `get()` in `DATA_MODEL.md` beside the rule summary, so
   the constraint is visible to whoever next edits that rule.

## Low

### L-1 — `timeEntries` now resolves to `[]` for ordinary members, undocumented

The old unconditional subscription was already denied by rules for ordinary
members (`timeEntries` is admin/manager-only), so it was producing listener
errors. Gating it is a genuine improvement. But it is a behavior change outside
the four workstreams and is not mentioned in the handoff or changelog. Worth one
line, since a future reader will wonder why the array is empty.

### L-2 — File scope exceeded the workboard declaration

`docs/AI-WORKBOARD.md` declared four files; seven changed. `src/App.jsx` and
`src/pages/ActivityLogPage.jsx` are two lines each, correct, necessary
(the `useFirestore` signature change and the pagination cursor), and both are
listed in the handoff — so this is disclosure, not drift. Noting it only because
`App.jsx` is a declared central file and the board should have been updated.
